# Pilot 测试与修复工作规程

## 目的与适用范围

本规程用于固定资产质检 Agent 进入真实底稿 Pilot 测试后的结果复核、问题确认、修复、回归和汇报。它负责串联以下既有规则，不替代原文：

- 写入和沟通确认：[`agent-collaboration.md`](agent-collaboration.md)
- 问题审计、状态、P0–P3 和修复队列：[`repair-queue-system.md`](repair-queue-system.md)
- L1–L5 测试选择：[`testing-regression-strategy.md`](testing-regression-strategy.md)
- 运行链路和规则准入：[`architecture/fa_qc_governance_plan.md`](architecture/fa_qc_governance_plan.md)
- Excel 标注副本：[`workpaper-annotation.md`](workpaper-annotation.md)

本规程不扩展 Frozen Repair Queue 的分类、状态或 P0–P3 口径。

## 核心原则

1. **Agent 输出是被测试对象，不是标准答案。**
2. **用户逐条确认后的结论是当前 Pilot 的标准答案。**当前不要求另有一份质检人员 findings 清单。
3. 原质检“无 findings”通常表示没有重大审计风险 findings，不代表底稿完全没有规范性提示。
4. 大模型独立复查只能形成“疑似漏报候选”，用户确认后才能登记为 Agent 漏报。
5. 没有锁定标准答案时，只汇报已确认数量，不汇报正式准确率或漏报率。
6. 修复前先只读追踪真实代码链路，选择最低正确层的最小系统性修复，不做单案例补丁。
7. Excel 标注副本是必交付物，其格式、定位和原底稿完整性与 finding 准确性分轨审计、分轨修复。

## 一、版本、构建、测试批次和回归轮次

四类编号分别管理，不相互替代：

| 字段 | 示例 | 更新条件 |
| --- | --- | --- |
| 产品版本 | `0.1.0` | 功能阶段或正式发布时更新 |
| Pilot 构建版本 | `PILOT-20260715.01` | 一组经确认的代码修改完成、准备重新测试时更新 |
| 测试批次 | `B20260715-01` | 新增一批测试底稿时更新 |
| 回归轮次 | `R1`、`R2` | 同一批底稿在修复后重新运行时更新 |

### 版本锁定条件

每个可测试构建至少记录：

- 产品版本和 Pilot 构建版本；
- Git commit；
- 工作区是否为 `dirty`；
- 规则版本或 registry 摘要；
- LLM 模型、提示词版本和关键配置；
- 测试日期、测试批次和回归轮次。

优先使用已确认的 Git 提交形成干净基线。若尚未提交，必须保留相关代码和配置摘要，并在版本中明确标注 `dirty`，不得只记录 commit 后声称版本已锁定。

第 1 批运行 28–40 暂记为“历史批次，版本未锁定”：可用于发现和分析问题，不用于严格衡量版本提升幅度。

### 版本展示与运行留痕

版本能力由统一版本信息驱动，并保持一致：

```text
统一版本信息
→ 报告 JSON
→ 运行历史
→ UI 顶部和运行详情
→ Excel QC_执行追溯页
```

历史运行没有版本信息时显示“历史未记录”，不得事后猜测或用当前版本倒填。

截至2026-07-15，版本追溯核心链路已落地：

- 当前产品版本为`0.1.0`，Pilot构建号为`PILOT-20260715.01`；
- UI左下角展示当前程序版本和锁定状态，复核结果页展示所选运行的运行版本；
- 新运行把产品版本、Pilot构建号、代码标识和锁定状态写入报告JSON及SQLite运行记录；
- 标注Excel的`QC_执行追溯`页记录同一版本快照；
- 运行28–40保留原数据并显示“历史未记录”；
- 当前构建因工作区为`dirty`仍显示“未锁定”，完成最终Git锁定前不得作为严格版本提升比较基线。

每次形成新的正式测试构建时必须递增Pilot构建号；新运行只追加版本快照，不覆盖旧运行。测试批次和回归轮次继续在Pilot测试台账中独立管理，不能用Pilot构建号替代。

## 二、标准答案与问题口径

### 标准答案形成方式

当前 Pilot 不依赖独立质检 findings 清单，采用以下流程：

1. Agent 先检查底稿并产生候选问题。
2. 用户结合底稿证据逐条判断。
3. 用户确认后的结论进入锁定标准答案。
4. 如需检查漏报，由大模型或 checklist 进行相对独立的第二遍复查，只产生疑似漏报候选。
5. 疑似漏报经用户确认后，才作为 Agent 漏报进入统计和修复队列。

### 人机比较口径

| 口径 | 定义 |
| --- | --- |
| 人机共同识别 | 原有人工记录和 Agent 均识别，且用户确认属实 |
| Agent 独立发现 | 原有人工记录未包含，Agent 识别且用户确认属实 |
| Agent 误报 | Agent 识别，但用户确认不构成问题 |
| Agent 漏报 | 独立复查发现、Agent 未识别，且用户确认属实 |
| 资料不足 | 当前证据无法判断，不计入误报或漏报 |
| 待确认 | 尚未完成人工判断，不进入准确率或漏报率 |

确认属实的问题继续区分“高风险问题”和“规范性提示”，不得把规范性提示数量并入高风险汇报。

### 第 1 批建议复核顺序

1. 高风险候选；
2. 疑似系统误判；
3. 资料不足；
4. 规范性提示。

## 三、台账写入和自动化边界

| 数据 | 责任方 | 写入规则 |
| --- | --- | --- |
| Agent 原始结果、运行编号、规则 ID、报告路径 | 系统 | 自动追加，不覆盖历史记录 |
| 问题簇归集 | 系统生成、用户复核 | 保留原始问题与问题簇的追溯关系 |
| 人工最终结论、问题性质 | 用户 | 用户确认后写入，记录复核日期 |
| 人机比较结果、复核进度、统计指标 | 公式或系统 | 只根据已确认字段自动计算，不单独人工改结果 |
| 根因和修复方案 | Agent 建议、开发确认 | 完成只读诊断后进入 Repair Queue |
| 修复版本、完成日期、回归结果 | 开发和实际测试结果 | 未修复或未运行不得提前填写 |

新增批次和回归轮次必须追加记录，不覆盖上一批原始运行。系统可以自动导入、归集、初分和统计，但不能自动批准真问题、误报、漏报或整改关闭。

## 四、修复前的系统级只读诊断

每个拟修复问题必须先沿真实执行链路检查：

```text
输入底稿
→ ingest：识别 sheet、区域、字段和金额
→ runner：选择执行路径
→ rules：执行判断
→ execution_ledger：记录运行事实
→ report：汇总和导出
→ annotation：定位并写入 Excel 副本
→ UI：展示已有结构化结果
```

只读诊断至少输出：

- 对应台账问题编号、底稿工作表和单元格；
- 当前真实代码调用链和相关测试；
- 问题最早在哪一层产生；
- 当前系统行为；
- 证据来源；
- 是否影响多个底稿、多个规则或多个输出；
- 根因及可能的替代根因；
- 建议修改层及为什么不在其他层修；
- 不修改范围；
- 推荐的 L1–L5 测试和业务验收标准。

“整体最优修复”是指在最低正确层做最小系统性修复，不等于未经确认扩大重构范围。

### 禁止的补丁式修复

原则上不得：

- 按真实客户名称、底稿文件名或运行编号写特殊条件；
- 按单个固定行号或单元格直接屏蔽问题；
- 在 report 或 UI 层隐藏 ingest/rules 的错误；
- 为减少 finding 数量而无依据地降低严重级别；
- 修改一个案例却不检查同类底稿和正常样本；
- 让 LLM 覆盖确定性规则结论。

确有模板例外时，应沉淀为可解释的 profile、结构识别条件或规则适用性条件，并补充正反案例测试。

## 五、问题审计与 Repair Queue

问题进入修复队列前，必须按 Frozen 规则具备：

- 问题分类；
- 当前系统行为；
- 至少一个根因；
- 证据来源；
- 影响范围；
- Frozen Architecture 归属；
- `CONFIRMED`、`SUSPECTED` 或 `UNKNOWN` 状态；
- 修改模块、逻辑、原因和不修改边界；
- 可验证的验收标准；
- findings、report、annotation/cmts 和跨模块影响检查；
- P0–P3 分级。

只有“已证实影响审计结论的错误”可以进入 P0。数量多、疑似风险或系统初判不得单独作为 P0 依据。测试覆盖和流程治理事项默认不作为业务 P0。

项目推进待办 T01–T09 不是 Repair Queue，不使用 P0–P3；只有逐条确认后的具体问题才进入 Repair Queue。

## 六、修改前沟通和执行锁定

Agent 请求修改授权时，必须按以下结构说明：

1. 一句话结论；
2. 对应问题编号和证据；
3. 只读代码链路和根因；
4. 拟修改文件、逻辑和原因；
5. 对 findings、report、annotation/cmts、UI 和历史数据的影响；
6. 不修改内容；
7. 推荐测试和验收标准；
8. 剩余风险。

只有用户明确回复“确认修改”“按此范围执行”等表达后才能写入。执行中如需增加文件、改变规则口径、改变 JSON/UI/数据库结构或扩大测试范围，必须停手并重新确认。

`git add`、`git commit`、`git push`仍需单独列清单并取得确认。

## 七、Excel 标注副本独立修复轨道

Excel 副本与 finding 准确性属于同一 Pilot，但分轨审计、分轨修复：

- 轨道 A：ingest、rules、LLM、pipeline 和 report 的识别准确性；
- 轨道 B：Comments、QC_Locator、单元格批注、格式和原底稿完整性。

Excel 副本至少检查：

- Comments 表的列宽、行高、换行、冻结窗格和筛选；
- finding 是否重复，合并粒度是否合理；
- 工作表顺序和隐藏状态；
- `Tab Ref.`、`Cell Ref.`和内部跳转；
- 单元格批注和高亮锚点；
- 原公式、外链、合并单元格、隐藏行列、原有批注和打印设置；
- 文件能否正常打开，UI 下载与本地产物是否一致；
- `QC_执行追溯`是否记录版本、构建、测试批次和回归轮次。

一般可读性问题通常为 P3；批注错写、原公式/外链损坏、finding 缺失或导致审计人员误解时，按实际影响升级。

## 八、分层测试与关闭条件

修复按[`testing-regression-strategy.md`](testing-regression-strategy.md)选择最小有效测试：

1. L1：目标函数或规则小测试；
2. L2：相关案例结构摘要；
3. L3：必要时整本 pipeline；
4. L4：涉及报告、UI或Excel副本时验收产物；
5. L5：大范围重构或正式发布前专项验收。

问题关闭必须同时满足：

- 代码修改完成；
- 针对性测试通过；
- 原问题样本回归通过；
- 至少一个正常样本没有新增误报；
- report 和 annotation/cmts 已检查或明确为 `N/A`；
- 修复版本、完成日期、回归批次和回归结果已记录；
- 剩余风险已说明。

“代码已改”不等于“问题已关闭”。

## 九、管理层汇报口径

每批固定汇报：

- 测试底稿数和运行成功率；
- Agent/Pilot构建版本、测试批次和回归轮次；
- 已复核/待复核问题数；
- 人机共同识别、Agent独立发现、Agent误报、Agent漏报；
- 确认高风险问题和确认规范性提示；
- 未关闭 P0/P1、已修复和回归通过数；
- 标准答案是否锁定。

正式准确率和漏报率只在标准答案锁定后展示；未完成全面独立复查时，漏报只报告已确认数量，不报告总体比例。

## 数据安全与沉淀边界

- 真实底稿、真实公司名称、`.env`、本地报告、标注副本和测试台账留在`local_data/`或本地资料目录，不提交 Git。
- 项目文档只记录脱敏统计、规则口径、修复方法和已确认结论。
- handoff 只保留当前状态、阻塞点、下一步和风险，不复制逐条真实问题。
