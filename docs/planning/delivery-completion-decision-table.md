# 交付完成度判定依据表（DL-001 / DL-002）

> 目的：把“交付完成度”从黑箱判断拆成可追溯的规则、证据和阈值。
> 适用范围：当前先覆盖 `DL-001` / `DL-002`，后续可扩展到所有 checklist。

## 1. 总体原则

- 交付阶段由 UI 明确选择：`首次交付` 或 `整体交付`。
- 细项判断尽量直接取自底稿、现有 findings、工作簿结构。
- 取不到证据时，优先输出 `NEED_REVIEW`，不硬判。
- `FAIL` 仅用于明确不满足交付完成度的情形。

## 2. 判定字段模板

| 字段 | 含义 |
| --- | --- |
| 检查点 | checklist 中的具体判断项 |
| 目标结论 | 该检查点希望达到的交付状态 |
| 输入来源 | 自动判断所依据的底稿 / findings / workbook 位置 |
| 自动判定条件 | 规则层直接判断的条件 |
| 阈值 / 口径 | 数量、比例或语义门槛 |
| 例外 / 兜底 | 无法稳定自动识别时的处理 |
| 输出映射 | `PASS / WARN / FAIL / NEED_REVIEW` 的落点 |

## 3. DL-001 首次交付标准

| 检查点 | 目标结论 | 输入来源 | 自动判定条件 | 阈值 / 口径 | 例外 / 兜底 | 输出映射 |
| --- | --- | --- | --- | --- | --- | --- |
| PSP 是否完成 | 主要实质性程序已完成 | `psp_completion` findings | 现有 `psp_completion` 仍有未闭环问题 | 只要存在非 `PASS` 的 PSP finding 即视为未完成 | 若工作簿结构无法识别汇总页，保留 `NEED_REVIEW` | 未完成程序 → `FAIL`；信息不足 → `NEED_REVIEW` |
| TOD/cutoff 是否已开始形成支持性证据 | 至少已部分获取详细测试/截止性测试证据 | `K.03.2`、`K.02.1` 样本证据列、K.03 TOD 内容识别、相关 findings | 能从底稿中识别到样本且存在证据描述 / 差异 / 属性结果等 | “完全未获取”视为失败；“已有样本但证据为空”视为失败；无法稳定识别时只给复核 | 若 workbook 读不到或样本口径不完整，输出 `NEED_REVIEW` | 完全未获取 → `FAIL`；已有部分证据 → 可通过；识别不稳 → `NEED_REVIEW` |
| 重大错报风险是否已识别并应对 | 重大风险事项已形成应对 / 调整记录 | `lead` findings、调整相关 findings | 现有错报风险/调整相关 findings 无未闭环问题 | 复用现有 `AE-001/AE-004/MT-003` 等相关 finding 语义 | 若仅能看见风险但不能判断应对充分性，保留 `NEED_REVIEW` | 存在未闭环风险/调整 → `FAIL`；仅缺判断证据 → `NEED_REVIEW` |

### DL-001 解释

- 这不是“检查所有底稿都完不完整”，而是检查“首次交付是否已满足继续推进的最低门槛”。
- 其中最硬的两个口径是：
  - `PSP` 不能还挂着未完成项。
  - 详细测试 / 截止性测试不能完全没有支持性证据。

## 4. DL-002 整体交付标准

| 检查点 | 目标结论 | 输入来源 | 自动判定条件 | 阈值 / 口径 | 例外 / 兜底 | 输出映射 |
| --- | --- | --- | --- | --- | --- | --- |
| Comments 是否全部清理 | 底稿副本不再保留未清理批注 / 未解决标记 | 工作簿批注、Comments 类 sheet、未解决文本 | 扫描 workbook，发现批注、review notes、open items、未解决标记即记残留 | 任一可识别残留都视为未清理 | 若工作簿不可读，输出 `NEED_REVIEW` | 有残留 → `FAIL`；不可读 → `NEED_REVIEW` |
| 未获取并检查支持性样本数是否超过 50% | 未完成样本不超过总样本的一半 | `K.02.1 新增选样输出`、`K.02.1 新增测试`、后续可扩展 K.02.2 / K.03 | 统计样本总数与已有证据样本数，计算未完成比例 | `unfinished / total > 50%` 视为不合格 | 若无法稳定识别分子分母，输出 `NEED_REVIEW` | 超过 50% → `FAIL`；无法识别 → `NEED_REVIEW` |
| 底稿程序是否全部完成 | 主要程序不再有未闭环缺口 | `psp_completion`、`addition_test_package_complete`、`disposal_test_package_complete`，后续可扩展 K.03 | 现有程序完整性 findings 中存在未闭环问题 | 以现有程序完整性 findings 为准 | 若某程序未建规则，则先不硬判，保留 `NEED_REVIEW` | 程序未闭环 → `FAIL`；规则未覆盖 → `NEED_REVIEW` |
| 审计调整是否均已确定 | 调整事项不再悬而未决 | 调整相关 findings、Lead 相关 findings | 发现仍有未确定调整 / 未提示项目组的事项 | 以现有调整相关 finding 为准 | 若只能看到“有调整”但无法判断是否已确定，输出 `NEED_REVIEW` | 未确定调整 → `FAIL`；判断不足 → `NEED_REVIEW` |

### DL-002 解释

- 整体交付更像“最终提交门槛”。
- 这组规则里，`Comments 清理` 和 `样本证据比例` 是最适合自动化的两个点。
- “程序是否全部完成”优先复用现有 findings，不再重复造一套口径。

## 6. 后续扩展建议

- 给每个 checklist 点补同类判定依据表。
- 再把每张表拆成：
  - 输入来源
  - 自动规则
  - 人工复核
  - 输出结论
- 等整套表稳定后，再决定是否回填到 `qc-checklist.md`、规划文档或规则字典说明里。
