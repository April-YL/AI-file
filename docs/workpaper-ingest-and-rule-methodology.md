# 底稿识别与质检规则开发方法论

本文用于指导后续 Lead、K.01、K.02、K.03 等程序的 `ingest`、`report` 与 `rules` 开发，避免直接凭单个案例或单条 checklist 写规则。

核心原则：

```text
模板定结构，SOP 定口径，ingest 先读对，report 先展示，rules 再判对，案例回归校准，质检经验补例外。
```

## 一、模板定结构

开发一个程序前，先读取标准底稿模板，拆清楚底稿结构，而不是直接写规则。

需要确认：

- 涉及哪些 sheet，例如汇总页、Lead、K.01、K.02.1、K.02.1a、清单页等。
- 每个 sheet 有哪些模块、区块、表头、锚点和关键单元格。
- 哪些位置是总体金额、差异、Notes、样本列表、测试结论。
- 哪些列是主程序必需字段，哪些只是辅助列或给其他程序使用。
- 标准模板中是否存在合并单元格、续行、隐藏列、公式链接、跨表引用等易影响读取的结构。

产出建议：

- 程序模块矩阵。
- 关键锚点清单。
- 字段/金额/Notes 读取计划。

## 二、SOP 定口径

模板说明“底稿长什么样”，SOP 说明“程序为什么这样执行、怎样才算执行正确”。

读取 SOP 时，应区分三类信息：

- **基础操作指引**：程序必须完成的基础动作，例如获取清单、与后推表核对、调查超过 SAD 的差异。
- **进阶实操提示**：特殊业务场景和判断要求，例如不同新增方式是否应分总体、是否需单独设计程序。
- **易错点**：常见错误和高风险误判，例如把所有新增方式混成一个总体、差异未调查、仅用金额不重大作为拒绝执行理由。

产出建议：

- SOP 与 checklist 对照表。
- 自动化边界说明：哪些可由数据判断，哪些只能提示人工复核。
- `PASS`、`WARN`、`FAIL`、`NEED_REVIEW` 的适用口径。

## 三、ingest 先读对

在质检 Agent 中，`ingest` 是“读取底稿并整理字段”。如果读取错了，后续规则再精细也会误报或漏报。

`ingest` 开发优先级高于规则数量扩张。

需要先解决：

- sheet 类型识别：支持标准命名和实际案例中的名称变体。
- 表头识别：支持多行表头、合并单元格附近表头、历史年度后缀和系统导出字段。
- 区块边界：能定位主表、附表、Notes 区、check 区和抽样输出区。
- 字段映射：字段同义词应结合 sheet 类型，避免把业务单号误映射为资产编号。
- 金额读取：明确金额口径、正负号、合计行、差异行和公式结果。
- 置信度与兜底：识别不可靠时不要强判，应输出摘录或 `NEED_REVIEW`。

原则：

- 新增同义词优先改字段映射，不直接改规则。
- 版式变体优先沉淀为 profile 或锚点规则，不靠单个文件名硬编码。
- 无法稳定读取的数据，不应用于 `FAIL/PASS` 强判。

## 四、report 先展示摘录

规则成熟前，应先把 `ingest` 读到的关键结果展示给质检人员复核。

`report` 的作用不只是汇总 findings，也应帮助确认 Agent 是否读对底稿。

建议展示：

- 识别到的 sheet 和程序包完整性。
- 关键字段映射结果。
- 总体金额、差异、Notes、样本列表等摘录。
- 识别置信度、缺失区块、候选 sheet 排名。
- 需要人工判断的事项和原因。

好处：

- 先让质检人员确认“读对”，再逐步让规则“判对”。
- 便于区分问题来自底稿识别、规则口径还是审计判断。
- 有助于降低早期规则误报带来的干扰。

## 五、rules 再判对

`rules` 是“自动检查规则”。规则应建立在稳定的 `ingest` 结果之上。

规则来源顺序：

1. Checklist 定质检点。
2. SOP 基础操作指引定执行动作。
3. SOP 进阶提示和易错点定特殊场景与风险提示。
4. 案例回归定识别变体。
5. 质检人员经验补充风险优先级和例外口径。

规则落地分四类：

| 类型 | 示例 | 建议结论 |
| --- | --- | --- |
| 结构完整性 | 三表程序包是否存在、必需字段是否完整 | `FAIL` / `WARN` |
| 金额勾稽 | 清单合计 vs K.01、差异是否超过 SAD | `WARN` / `FAIL` / `NEED_REVIEW` |
| 说明充分性 | 不执行理由、差异 Notes、特殊事项说明 | `NEED_REVIEW`，可辅以 LLM |
| 审计判断 | 控制权转移证据是否充分、测试属性是否恰当 | `NEED_REVIEW` |

规则上线前必须回答：

- 数据来源是否稳定可读。
- 规则是否能明确区分错误与需人工判断。
- 是否会因命名、版式、Notes 写法变体导致大量误报。
- 是否有脱敏 fixture 或案例回归覆盖。

## 六、案例回归校准

标准模板只代表理想版式，案例库代表真实工作方式。

案例回归应同时验证：

- sheet 识别是否准确。
- 字段映射是否准确。
- 区块/金额/Notes 是否读对。
- 规则结论是否符合质检口径。
- 标注位置是否能定位到对应 sheet、行或单元格。

回归记录应区分失败原因：

- `ingest` 问题：没读到、读错 sheet、字段映射错、金额锚点错。
- `rules` 问题：规则口径错、严重级别错、自动化边界过强。
- `report` 问题：摘录不清楚、标注定位不准、问题合并粒度不合适。
- 业务判断问题：需要质检人员确认，不应强行自动判定。

## 七、质检经验补例外

质检人员经验非常重要，但不应直接覆盖 checklist 或 SOP。

经验应优先沉淀为：

- 高风险提示。
- 例外场景。
- `NEED_REVIEW` 条件。
- 后续规则候选。
- 案例回归重点。

只有当经验口径稳定、可由结构化数据支持，并通过案例回归验证后，才升级为 `FAIL/WARN` 自动规则。

## 八、开发检查清单

每新增一个程序或规则，至少检查：

- 是否已读标准模板并拆模块。
- 是否已读 SOP 基础操作、进阶提示和易错点。
- 是否明确 `ingest` 要读哪些 sheet、字段、金额、Notes。
- 是否先在报告中展示关键摘录。
- 是否明确规则来源和自动化边界。
- 是否补充或更新测试。
- 是否用案例回归验证识别准确性。
- 是否避免提交真实数据、`.env` 或密钥。

## 九、简要示例：K.02 新增测试

K.02 新增测试不应只检查是否存在 `K.02.1` sheet。

更稳妥的开发路径：

1. 模板识别：确认 `新增清单`、`K.02.1 新增测试`、`K.02.1a 新增选样输出` 三表程序包。
2. SOP 口径：新增测试总体通常为购置新增原值；其他新增方式需单独考虑程序。
3. ingest：读取新增清单字段、`addition_method`、原值合计、抽样输出页。
4. report：展示新增方式分布、清单字段映射、总体金额和三表完整性。
5. rules：先做字段完整性和程序包完整性，再做与 K.01 勾稽，最后做样本一致性和证据提示。
6. 案例回归：验证名称变体、系统导出清单、非购置新增和抽样输出页识别是否准确。
