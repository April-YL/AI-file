# ADR-0003：统一编排、LLM Router 与准确性治理

## 状态

已采纳（2026-07-16）。

本决策以当前 `main` 的真实执行链和 Pilot 两批测试为依据。它补充 ADR-0002，并取代旧方案中与本文冲突的编排、LLM 定位和规则准入口径；旧文档继续作为历史记录，不因曾被称为 Frozen 而自动高于当前决策。

## 背景

Pilot 第一批运行 28–40（13 张底稿）和第二批运行 41–57（17 张底稿）显示：Agent 输出多于原质检 findings 本身不等于误报，因为 Agent 同时覆盖审计风险和规范性提示。当前任务是区分真实问题、系统误报、系统漏报、资料不足和待人工确认，而不是消灭 findings。

第二批已确认多个批量异常问题簇。Run 43 的使用年限、残值率和新增清单，Run 54 的资产编号，以及 Run 52 的新增/处置清单均存在错误字段或错误量纲进入规则后产生大量确定性输出的情况；Run 52 还因工作表分类错误导致 FA list 核心规则未进入执行链。它们共同暴露的最低层根因不是多条规则同时失效，而是：

1. 工作表和字段识别过早返回单一最终答案，缺少候选、证据、拒绝理由和可信度验证。
2. 识别结果与规则之间缺少规则级 Readiness，错误输入会直接触发确定性 `FAIL`，未执行规则也可能不易察觉。
3. LLM 调用分散，缺少统一总开关、分能力开关、按规则控制、失败策略和调用追踪；现有识别复核发生较晚，无法阻止错误字段进入规则。
4. 报告层会放大上游批量异常，但不是上述问题的最低层根因。

## 决策目标

1. 优先提高质检准确性和稳定性，不以减少 findings 数量为目标。
2. 沿真实执行链找到最低层、最共同的根因，并在该层做最小系统性修复。
3. 错误或不可信字段不得产生确定性 `FAIL`；资料不足不得记为 `PASS`；规则未执行不得静默跳过。
4. LLM 是贯穿识别、规则和报告的一等能力，但必须接受统一编排、统一路由、结构化契约和审计追踪。
5. 报告、底稿标注、execution ledger 和 observation 必须反映同一次正式执行的事实，不建设第二条生产流水线。

## 目标执行链

```text
输入底稿
  → Orchestrator：统一组织一次正式运行
      → 确定性工作表/字段识别与候选证据
      → 必要时经 LLM Router 调用 identification 兜底
      → 系统验证字段采纳结果
      → Rule Readiness：逐条规则判断 READY / DATA_INSUFFICIENT / NOT_APPLICABLE
      → 规则执行
          ├─ 纯代码规则
          ├─ 纯 LLM 语义规则（经 LLM Router）
          └─ 代码 + LLM 联合规则（经固定合并策略）
      → 统一 Finding / ledger / observation
      → 报告、标注与可选 narrative
```

### Orchestrator

Orchestrator 是唯一正式执行链的编排者，负责阶段顺序、运行上下文、状态传递和失败降级。它不重新实现字段识别、业务规则或报告逻辑，也不自行生成审计结论。

### LLM Router

LLM Router 是所有 LLM 能力的唯一调用入口，不是通用业务 Router，也不是报告专属工具。它至少统一管理：

- LLM 总开关，默认关闭；
- `identification`、`rule_review`、`hybrid_rule`、`narrative` 分能力开关；
- 按规则启停和允许的调用用途；
- provider、model、提示词版本、超时、重试、结构校验和失败降级；
- 不含密钥、完整提示词和原始底稿的最小调用追踪。

UI、CLI 和配置文件必须进入同一配置对象，不能形成各自独立的开关或模型配置。

## 识别与规则准入

工作表和关键字段识别应保留候选、选择结果、位置、证据、反证、采纳或拒绝理由以及识别来源。关键或歧义字段应至少满足两类独立系统证据，例如表头语义、值类型、值分布和结构上下文；LLM 输出本身不单独构成采纳证据。

LLM 可在确定性识别存在歧义时判断表头语义、上下文结构和样本值含义，并输出候选选择、理由、置信度和引用位置。系统必须再次验证其结果；验证不通过时只允许对受影响工作表或字段进行最多一次局部确定性重整，仍不可靠则固定降级为 `NEED_REVIEW` / `DATA_INSUFFICIENT`。

Readiness 必须按规则判断，而不是对整本底稿一刀切。每条规则声明所需资料、字段、最低证据、是否允许 LLM 参与以及资料不足时的降级动作。聚合 `NEED_REVIEW` 可以降噪，但必须保留全部受影响规则、阻断字段和具体原因。

## 三类规则

1. **纯代码规则**：金额勾稽、唯一性、必填和可结构化一致性等确定性检查，由代码基于已验证字段执行。
2. **纯 LLM 语义规则**：需要阅读说明、政策或审计结论的检查，必须在 registry 登记、通过 LLM Router 调用并产生结构化结论和依据；调用失败时降级为 `NEED_REVIEW`，不得静默通过。
3. **代码 + LLM 联合规则**：代码负责读取事实和计算，LLM负责规定范围内的语义判断，系统按注册的固定策略合并；LLM失败时保留确定性事实并将未完成部分降级为 `NEED_REVIEW`。

LLM 不得绕过 registry 和 Orchestrator 直接生成正式 finding，也不得无依据把确定性 `FAIL` 改为 `PASS`。现有 Lead 调整分录中 LLM 影响严格金额检查准入的行为属于待迁移兼容例外，迁移时必须显式记录并最终拆分为识别、Readiness 和语义判断。

## 修复和验收原则

禁止按公司、文件名、运行编号、固定行列或单元格地址增加特例；禁止用 finding 数量上限、统一放宽阈值、缺失即通过或“所有数值 5 均除以 100”等方式掩盖问题。

实施顺序固定为：

```text
工作表与字段识别
→ 字段可信度与 Rule Readiness
→ Orchestrator / LLM Router 统一控制
→ 具体规则计算和语义
→ Finding、报告和标注
```

验收至少覆盖：错误字段不产生确定性 `FAIL`、资料不足不变成 `PASS`、规则不静默跳过、同输入重复运行一致、真实问题继续保留、报告与标注锚点一致。新旧对比只在测试中比较标准化的已执行规则、跳过规则、findings、ledger 和标注锚点，不建设生产双流水线。

## 范围边界

本阶段将 FA list 纳入，是为修复 Run 43、52、54 等样本中已确认的批量误报和检查覆盖漏失，不代表 FA list 重新成为长期开发主线；K.00–K.03 既有程序口径、规则优先级和演进方向不变。

当前沉淀只确立目标和治理约束，不代表相应代码已经实现。Architecture Guard 应在目标结构通过回归后最后收口，不能让旧 Guard 阻止合理演进。
